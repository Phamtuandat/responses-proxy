# CI/CD plan for responses-proxy

## Goal
Add a lean CI/CD pipeline for `responses-proxy` only, so changes are validated automatically and a production artifact can be built and deployed repeatably.

## Current context
- Repo: `responses-proxy`
- Existing production/deployment surface already includes:
  - `Dockerfile`
  - `docker-compose.yml`
  - `package.json` scripts for build, test, and app lifecycle
  - `README.md`
  - `docs/public-bot-production-release.md`
  - `skills/hermes-omv-production/SKILL.md`
- The repo currently does not show a `.github/` workflow directory.
- The app already has buildable server/client output and health endpoints.
- The current compose file includes more than the proxy service, but this plan is scoped to the proxy only.

## Scope
In scope:
- CI for lint/typecheck/test/build of the proxy app
- Container image build for the proxy
- Optional deploy job for OMV or another Docker host
- Basic release/version tagging and artifact traceability

Out of scope for this plan:
- Telegram bot deployment flow
- Hermes/Codex mount design
- Product behavior changes
- Runtime refactors unrelated to CI/CD

## Proposed CI/CD shape
Use GitHub Actions with two or three workflows:

1. CI workflow on pull requests and pushes to main
   - install dependencies
   - run typecheck
   - run tests
   - run build
   - optionally build the Docker image without pushing it

2. Container publish workflow on tags or main releases
   - build the proxy image from `Dockerfile`
   - push to a registry such as GHCR
   - attach immutable metadata labels

3. Optional deploy workflow for OMV
   - pull the published image on the OMV host
   - restart only the proxy service
   - run a health check against `/health`

## Step-by-step plan

### 1) Define the deployment target clearly
Decide whether the primary CD target is:
- GHCR + manual OMV pull, or
- direct SSH deployment to OMV, or
- compose-driven pull on host

Default recommendation: publish to GHCR, then update OMV by pulling the tagged image.
This keeps CI deterministic and the OMV host simple.

### 2) Add a CI workflow
Create `.github/workflows/ci.yml` that runs on:
- `pull_request`
- `push` to `main`

Jobs should:
- set up Node 20
- install deps with `npm ci`
- run `npm run check`
- run `npm test`
- run `npm run build`
- optionally run a Docker build for the proxy image

If the build is noisy, keep the CI job focused on the proxy package and not the full deployment stack.

### 3) Add container build/publish workflow
Create `.github/workflows/docker-publish.yml` that runs on tagged releases or release branches.

Responsibilities:
- build the image from `Dockerfile`
- tag with commit SHA and semver tag if present
- push to registry
- add labels for source, version, revision, and build date

Recommended registry behavior:
- `ghcr.io/<owner>/responses-proxy:sha-<shortsha>`
- `ghcr.io/<owner>/responses-proxy:latest` only for the main release channel
- semver tags when publishing official releases

### 4) Make the image deploy-friendly
Review `Dockerfile` and make sure the runtime image is minimal and stable for CI/CD.
Potential adjustments:
- ensure build args/labels are supported
- keep `npm ci` deterministic
- make sure `dist/server.js` is the only required runtime entrypoint
- avoid copying unnecessary files into the runtime image

### 5) Decide how OMV consumes the artifact
For OMV, pick one of these deployment patterns:
- manual `docker compose pull && docker compose up -d responses-proxy`
- SSH-based deploy job that runs the same commands remotely
- Watchtower or a similar auto-update pattern if that is acceptable

Recommended default:
- keep OMV pull-based and explicit
- do not auto-update without a deliberate tag or approval step

### 6) Add deployment verification
After deploy, run:
- `curl http://127.0.0.1:8318/health`
- `docker compose ps`
- `docker compose logs --tail=50 responses-proxy`

If using a pipeline job, fail the deploy stage if `/health` does not return `ok: true`.

### 7) Document the release flow
Update `README.md` or a new `docs/deployment.md` with:
- how to run CI locally
- how tags map to container versions
- how OMV updates are applied
- rollback procedure to the previous image tag

## Files likely to change
- `.github/workflows/ci.yml`
- `.github/workflows/docker-publish.yml`
- optionally `.github/workflows/deploy-omv.yml`
- `Dockerfile`
- `README.md`
- optionally `docs/deployment.md`
- optionally `docker-compose.yml` if image references are introduced

## Validation plan
Local validation before merging:
- `npm ci`
- `npm run check`
- `npm test`
- `npm run build`
- `docker build -t responses-proxy:ci .`
- container smoke test: start image and hit `/health`

Pipeline validation after merge:
- confirm workflow passes on PR and main branch
- confirm image is published with the expected tags
- confirm OMV can pull and restart the proxy service successfully
- confirm health endpoint still returns `ok: true`

## Risks and tradeoffs
- If the workflow builds the whole repo, unrelated bot code may slow down or fail the proxy pipeline.
- If the deploy job is fully automated, a bad main branch could roll to OMV too quickly.
- If compose still points to `build: .`, CD may not benefit from the registry unless the compose file is updated to use an image tag.
- If secrets are not scoped carefully, registry or deploy credentials could be exposed to the wrong jobs.

## Open questions
- Should deployment target OMV only, or should the same pipeline support another environment later?
- Should releases be manual GitHub releases or automatic on `main`?
- Should the compose file switch from local build to pinned image tags for production?
- Do you want a hard rollback plan in the workflow itself, or only documented rollback commands?

## Success criteria
- Every PR to the proxy gets CI coverage.
- Main branch builds produce a deployable image.
- OMV can update the proxy from a tagged image without manual rebuilds.
- `/health` remains the post-deploy gate.
