# OMV deployment plan for responses-proxy

## Goal
Deploy `responses-proxy` on an OMV host with Docker Compose so the proxy, Telegram bot, and worker run persistently, keep state under `./logs`, and expose Hermes through the proxy endpoint.

## Current context
- Repo root: `responses-proxy`
- Deployment model already exists in `docker-compose.yml`
- Production guidance exists in:
  - `.env.production.checklist`
  - `docs/public-bot-production-release.md`
  - `skills/hermes-omv-production/SKILL.md`
- The stack expects the proxy on port `8318`
- Hermes should use `http://127.0.0.1:8318/v1` locally or the public proxy URL in production

## Assumptions
- OMV host has Docker and Docker Compose available.
- The repo will live in a persistent OMV shared folder or another persistent mount.
- `HOME` on the OMV host points to the real account home that contains `~/.hermes/config.yaml` and `~/.codex`.
- Public bot mode is desired unless the user says otherwise.

## Proposed deployment approach
Use the existing Compose stack instead of inventing a new deployment layout.

Primary services:
- `responses-proxy`
- `telegram-bot`
- `telegram-bot-worker`

Persistent storage:
- `./logs:/app/logs`
- host Hermes config mount: `${HOME}/.hermes/config.yaml:/host-home/.hermes/config.yaml`
- host Codex mount: `${HOME}/.codex:/host-home/.codex`

## Step-by-step plan

### 1) Prepare the OMV host workspace
- Choose a persistent folder for the repo on OMV.
- Clone or copy `responses-proxy` there.
- Confirm Docker storage and the repo path are on persistent disk, not tmp.
- Make sure the OMV user running Compose has access to the repo and mounted config files.

### 2) Populate deployment environment
- Start from `.env.production.checklist`.
- Fill in real values for:
  - `UPSTREAM_BASE_URL`
  - `UPSTREAM_API_KEY`
  - `TELEGRAM_BOT_TOKEN`
  - `TELEGRAM_OWNER_USER_IDS`
  - `RESPONSES_PROXY_CLIENT_API_KEY`
  - `BOT_PUBLIC_RESPONSES_BASE_URL`
- Keep these aligned with production mode unless intentionally changing behavior:
  - `BOT_PUBLIC_SIGNUP_ENABLED=true`
  - `BOT_REQUIRE_ADMIN_APPROVAL=false`
  - `BOT_BOT_MODE=polling`
  - `LOG_BODY=false`
- Leave emergency lockdown lists empty unless needed.

### 3) Verify OMV host mounts and paths
- Confirm the host has:
  - `~/.hermes/config.yaml`
  - `~/.codex/config.toml`
  - `~/.codex/auth.json` if used
- Verify the mounts resolve correctly inside the container as `/host-home/.hermes/...` and `/host-home/.codex/...`.
- If `HOME` is not correct under OMV, fix the environment before starting the stack.

### 4) Bring up the stack
Run Compose from the repo directory:

```bash
docker compose up -d --build responses-proxy telegram-bot telegram-bot-worker
```

If the OMV workflow prefers a single-shot bootstrap, use the same command there.

### 5) Verify the deployment
Check these in order:
1. Container state
   - `docker compose ps`
2. Proxy health
   - `curl http://127.0.0.1:8318/health`
3. Proxy logs
   - `docker compose logs --tail=100 responses-proxy`
4. Bot logs
   - `docker compose logs --tail=100 telegram-bot`
   - `docker compose logs --tail=100 telegram-bot-worker`
5. App access
   - confirm the dashboard loads at `/`
   - confirm the proxy is reachable at `/v1`
6. Data persistence
   - confirm SQLite files appear under `./logs`

### 6) Verify Hermes wiring
- Point Hermes at the proxy base URL, not the upstream provider directly.
- Confirm the configured base URL is the proxy endpoint ending in `/v1`.
- If running locally on the OMV host, use `http://127.0.0.1:8318/v1`.
- If using a public host, update the production base URL accordingly.

### 7) Operational checks after first boot
- Restart the stack once to ensure persistence behaves correctly.
- Confirm the bot still starts cleanly after restart.
- Confirm the worker continues to run and complete a cycle.
- Confirm logs do not show auth, upstream, or mount errors.

## Files likely involved
For deployment prep, not app code:
- `.env` on the OMV host
- `docker-compose.yml`
- `./logs/`
- host-mounted `~/.hermes/config.yaml`
- host-mounted `~/.codex/`

## Risks and tradeoffs
- If `HOME` is wrong on OMV, the host config mounts will silently point at the wrong place.
- If `BOT_PUBLIC_RESPONSES_BASE_URL` is not public/reachable when required, the public bot flow will fail for customers.
- If `./logs` is not on persistent storage, bot/session state will be lost on restart.
- If the OMV host runs a reverse proxy or nonstandard port mapping, port `8318` may need adjustment.
- If the user wants only the proxy and not the Telegram stack, the Compose service set should be narrowed before deployment.

## Open questions
- Should this OMV deployment expose the proxy only on LAN, through Tailscale, or publicly?
- Should the Telegram bot run in public-signup mode or restricted operator mode?
- Is the OMV host the same machine that owns `~/.hermes` and `~/.codex`, or do those need to be copied/mounted differently?

## Success criteria
- `responses-proxy` responds on port `8318`
- `/health` returns `ok: true`
- Telegram bot and worker both start without fatal errors
- `./logs` contains persistent database files
- Hermes can use the proxy endpoint as its base URL
